# 20261111-2035-nat64-lan-checksum NAT64-LAN recomputes transport checksums and hides corruption

- **status**: completed
- **priority**: P2
- **owner**: audit-fix
- **createdAt**: 2026-11-11 20:35

## Description

Audit finding: `nat64_lan/packet.rs` zeroed the TCP, UDP and ICMP checksum field and recomputed
it over the translated packet in both directions without verifying the incoming one. A segment
corrupted before the translator left with a valid checksum, and every packet paid a pass over
its payload. `translate/rfc7915.rs` already updates incrementally (RFC 1624).

Acceptance: TCP and UDP checksums are updated incrementally for what changes (pseudo-header,
port, clamped MSS); a corrupted packet stays corrupted on output in both directions; an IPv4
UDP reply without a checksum gets a full IPv6 one; a computed UDP zero is sent as `0xFFFF`;
zero TCP and ICMP checksum fields stay ordinary values.

## ActiveForm

Moving the NAT64-LAN translator to incremental checksum updates.

## Notes

- TCP and UDP: `update_pseudo_header` between the IPv6 and IPv4 pseudo-headers plus `update_u16`
  for the rewritten port. The MSS clamp updates the checksum itself, with the bytes swapped
  for an option value at an odd offset.
- ICMP echo is incremental too: the helpers cover it (the `ICMPv6` pseudo-header is added or
  removed with `update_u16` against a zero sum, then the type word and the identifier are
  replaced). This path translates echo only, so there is no quoted packet to rewrite. The
  generated Packet Too Big is a new packet and keeps its full computation.
- An IPv6 UDP request with a zero checksum field is dropped as `MALFORMED` (it used to leave
  with a freshly computed checksum). `rfc7915.rs` rejects it the same way; an incremental
  update would otherwise turn it into an IPv4 datagram without a checksum.
- The incoming checksum is not verified, unlike `rfc7915.rs`: the requirement is that
  corruption stays detectable by the receiver, and verifying would keep the pass over the
  payload.
- Not changed: the hop limit and TTL are copied without a decrement (documented in the module
  as the forwarding node's job), and fragment handling.
