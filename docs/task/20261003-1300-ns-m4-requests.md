# 20261003-1300-ns-m4-requests Engine hooks requested by ns account mode (M4)

- **status**: pending
- **priority**: P1
- **owner**: (unassigned)
- **createdAt**: 2026-10-03 13:00

## Description

ns runs account mode on the engine behind a runtime switch (ns migration M4). The
engine path ships without direct P2P and recovery probes: ns's link ladder needs to
send on a chosen path and to know which path a packet arrived on. These hooks would
close that gap and a few smaller ones found during M4.

Ladder (needed before ns can make the engine path its default):

1. `EngineHandle::inject_outbound_on(peer, path, packet)`: send one packet on an
   explicit path, bypassing `PathPolicy::select`. Used for path validation bursts and
   recovery-probe replies while user data stays on the current path.
2. Receive-path attribution for decrypted inbound packets: the path in the
   `PacketFilter` inbound context, or per-path payload counters in `PeerStats`.
3. A `PathPolicy` hook for authenticated messages on the current path, so the ladder
   can adopt a direct path normally and observe loss on it.

Netstack:

4. Blocking accept (backpressure) as an option instead of dropping after the
   128-entry backlog.
5. `connect_tcp` with a caller-chosen local port (ns reserves host ports for
   exit-owned runtimes).
6. A random start for ephemeral local ports per stack.

Conditional (filed only if ns M4 measurements show account traffic hitting it):

7. Per-peer opt-out of the inbound `SOURCE_NOT_ALLOWED` check (accept any source from
   that peer and leave the decision to the filters), for forwarded or relayed sources.

## Proposal

Inputs: the docs site (`ns/account.md` §2.4 link ladder and direct promotion,
`ns/quick-v2.md` §9 probes, `architecture.md` §5.2 transport modes, `migration.md` M4) and
ns's ladder (`crates/overlay/src/ladder.rs`).

How the ladder uses the engine today, and the gaps:

- Direct promotion needs probe traffic on a candidate while user data stays on the relay:
  account mode sends three rounds of 16 encrypted 1200-byte outer packets to the exact
  candidate endpoint; quick-v2 sends `PROBE_REQUEST` at most every 250 ms per candidate.
  `PathPolicy::select` can only steer by message kind, so ns sends handshakes and
  keepalives to the candidate and cannot send a burst there (item 1).
- quick-v2 §9 promotes a candidate only on a `PROBE_REPLY` with a live nonce that came from
  the exact attempted tuple under the current session. The reply is an in-tunnel control
  packet (UDP 47900) a `PacketFilter` consumes (`Handled`), and that filter does not know
  the path the packet arrived on (item 2). Today ns confirms with any authenticated message
  from the candidate (`AuthenticatedProbe`, a documented gap), and the replying side cannot
  answer `PROBE_REQUEST` on the tuple it came from.
- A confirmed direct path is lost after 15 s of data sent without an authenticated message
  received on it. The core asks the policy only about messages from a path other than the
  peer's current one, so ns pins the engine path to the relay and steers data with
  `select` to see every message on the direct path (item 3).

Design (each hook additive, defaults unchanged, no cost when unused):

1. `Core::inject_outbound_on(peer, path, packet, now)` and
   `EngineHandle::inject_outbound_on(peer: PeerId, path, packet)` (by `PeerId`, like
   `inject_inbound` and `force_handshake`): seal `packet` for
   `peer` in its current session and transmit it on `path` (ECN `NotEct`), bypassing
   routing, the outbound filters and `PathPolicy::select`; the peer's path and its
   handshake timers are unchanged. Without a current session the packet is dropped as the
   new `reasons::NO_SESSION` (no queuing, no handshake towards the probe path: direct only
   competes after an authenticated session). With crypto workers it keeps the per-peer
   order like any other packet.
2. `PacketFilter::inbound_from(&self, peer, from: &Path, packet) -> Verdict` with a default
   that calls `inbound`; the core calls it for every decrypted datagram (single, batched
   and deferred paths), with the path the datagram arrived on. Packets from
   `inject_inbound` skip the filters as before. Not chosen: a path argument on `inbound`
   (breaks every filter) and per-path counters in `PeerStats` (unbounded per peer, and they
   cannot correlate a nonce with its tuple).
3. `PathPolicy::observe_every_message(&self) -> bool` (default `false`, read once when the
   core is built): when `true`, `on_authenticated` is called for every authenticated
   message (not cookie replies), on the current path too; its `Roam` is ignored when the
   path is already current. `Event::Authenticated` stays limited to path changes. ns can
   then make the confirmed direct path the engine path and keep its loss timer from the
   callbacks.
4. `NetStackConfig::accept_backpressure` (default `false`): while a port's accept queue is
   full, new SYNs to it are left unanswered (counted `syn_deferred`, the peer retransmits)
   and connections that completed their handshake wait in the stack until accepted, instead
   of being closed (`tcp_not_accepted`). UDP flows keep dropping.
5. `NetStackHandle::connect_tcp_from(local_port, remote)`: `AddrInUse` when the port is
   taken by a connection or listener of the stack.
6. Ephemeral TCP and UDP ports start at a random point of the range per stack (from the
   stack's random seed) instead of the range start; port 0 semantics are unchanged.
7. Not done now (conditional on ns M4 measurements).

Workstreams: MA core + engine (1-3, `crates/nsplane-core/**`, `crates/nsplane/src/**`,
e2e), MB netstack (4-6, `crates/nsplane-netstack/**`, e2e). Disjoint; parallel.
