## Context

Release 0.9.0 closed the ns requests. Quiet-host comparison on 0.8.0 main (Gbit/s, 1 / 4 TCP
streams): nsplane <-> nsplane 8.12 / 8.93, wireguard-go 9.99 / 10.14, kernel WireGuard 4.04 /
4.10, nsplane without offload 3.13 / 3.41, netstack <-> netstack 6.21 / 2.02 (four streams
slower than one). Baselines for this round are re-measured on 0.9.0 at the start
(`.tmp/baseline-0.9.0/`, load recorded) and summarized in the annotations.

Follow-ups collected in earlier plans (`20261003-1630-perf-and-wss`,
`20261004-1100-ns-requests`) are the remaining input. Conventions as always: defaults keep
today's behavior unless the change is a pure speedup, nothing new costs a basic client
anything, every existing guarantee of the engine holds (per-peer order, bounded queues,
backpressure, counted drops, suspend/resume, runtime transports, cancellation safety), no new
dependency, no `unsafe` outside `nsplane-tun` / `nsplane-noise`.

## Proposal

### OE: engine and device fast path

Profile nsplane <-> nsplane single and four streams in the bench harness (perf in the dev
image, flamegraphs attached) and fix what the profile shows. Known candidates:

- sealing and pool allocation on the send path (buffer reuse, fewer copies);
- the TSO split copy in `nsplane-tun` (segment in place or into pooled buffers);
- TUN write coalescing on the receive path (GRO into the device where offload allows);
- a pooled-buffer length setter without zero-fill (a design without `unsafe` in
  `nsplane-packet`, or a short note why it is not possible);
- multi-stream scaling: why four streams gain little over one (owner task, worker pool,
  transport batching).

Design note to L1 before coding the engine changes (yellow gate). The 0.9.0 baseline already
puts the default pair at par with wireguard-go (see Annotations), so the targets are the weak
spots: crypto workers (throughput and UDP loss), the no-offload per-packet cost, the mixed
directions with kernel WireGuard, loaded latency, and CPU per GB. Acceptance: measurable gains
in quiet A/B pairs against main on those targets, P1/P4 kept, no idle-latency regression, no
regression in data_path, worker_pool, local_graph, udp_offload and tun offload benches.

### ON: netstack throughput

- The four-stream anomaly (6.21 -> 2.02 Gbit/s) and the UDP loss in the netstack pair: find
  the cause (driver turn fairness, queue sizes, window behavior) and fix it.
- The smoltcp-fork round on `dotns/smoltcp`: the checksum loop over u64 words (about 15 % of
  stack instructions), SACK or NewReno partial-ACK retransmit, the furthest-advertised
  window edge. Changes to the fork go on a branch of the fork and the workspace points to
  the new revision (yellow to L1 before the fork is pushed; upstreaming stays the user's
  call, open item #19).

Acceptance: the netstack pair with four streams at least as fast as one, UDP loss explained
or reduced, `netstack_lossy` and the netstack tests green, before/after in the harness.

### OH: hygiene follow-ups

- `crates/nsplane-acl/src/filter.rs`: the runtime `unreachable!` in the flow table entry
  lookup becomes an error path (counted drop), with a test.
- `nsplane-wss` `session_budget_bounds_all_streams` (crate and e2e): wait on progress instead
  of a timeout so it holds at load > 50.
- A UAPI listen-port / fwmark rebind honors `nsplane-cli --no-offload`.
- A coarse clock for the node L3 gate's flow table (established-flow cost, today 64-90 ns).
- The translator's zero-checksum reassembly moves onto `nsplane_packet::reassembly`.

Acceptance: a test per item; the node L3 bench before/after for the clock.
