## Context

ns measured the engine 15-21 % below its legacy tunnel-wg loops on a single TCP stream over
TUN (4.0 vs 4.7 Gbit/s, not CPU-bound; the extra time is in the task handoffs read_source ->
owner -> transmit and receive -> owner -> write_sink) and nsplane-netstack 12-14 % below the
legacy smoltcp stack (cause unknown; 1 MiB buffers did not close it). The user also asked how
nsplane compares with WireGuard implementations. Items MF-1, MF-2, MB-x5 and MC-3 of task
`20261003-1500-ns-dataplane-moves`, and ADR `2026-10-03-data-channel-protocols-in-nsplane`.

## Proposal

### PB: benchmark harness (first; the others measure with it)

`scripts/bench/wg-compare.sh` (+ `just bench-wg`), containers on a dedicated docker network
with pinned CPUs (`--cpuset-cpus`, one set per side, documented), real TUN devices:

| Pair | Variants |
|---|---|
| kernel WireGuard <-> kernel WireGuard | baseline |
| nsplane-cli <-> nsplane-cli | offload on/off; crypto workers 0/2 |
| nsplane-cli <-> kernel WireGuard | both directions |
| wireguard-go <-> wireguard-go | userspace reference (built from source in a labelled builder image `ai-agent/wireguard-go`; a test tool only, never a dependency) |
| nsplane netstack node <-> nsplane netstack node | user-space mode (an example binary with an iperf-style TCP/UDP load in-process, since iperf3 needs a kernel stack) |

Measurements: iperf3 TCP single stream and 4 streams (30 s), UDP at fixed rates with loss,
ping p50/p99 idle and next to a saturating flow, CPU seconds per GB per side (from cgroup
`cpu.stat`); 3 runs, medians, the load average recorded. Output: a markdown table appended
to a results file under the run directory and summarized in `docs/architecture.md`
(*Performance*, *Against WireGuard implementations*). The ns T10b numbers are the reference
for the legacy ns loops (not rebuilt here).

### PF: engine fast path (MF-1)

Fewer task handoffs on the hot path when no crypto workers are configured: e.g. the owner
reads local packets and received datagrams itself (or the source task seals and sends,
run-to-completion) and hands datagrams to the transport without the transmit-task hop when
the socket accepts them, falling back to today's queues and backpressure when it does not.
The design is the L2's, with a short design note to L1 before coding (yellow gate): it must
keep every existing guarantee (per-peer order, bounded queues, backpressure semantics, counted
drops, suspend/resume, transports added/removed at runtime, cancellation safety, worker pool
unchanged). Acceptance: PB's nsplane <-> nsplane TCP single stream improves measurably (target:
the ns gap closed, i.e. >= +18 % on the same harness, or a profile showing what is left), no
idle-latency regression, data_path no regression, every existing test green.

### PS: netstack throughput (MF-2, MB-x5)

Profile `nsplane-netstack` under a single TCP stream (perf in the dev image, flamegraph
attached to the report), fix what the profile shows, and add `NetStackConfig::tcp_rx_buffer`
/ `tcp_tx_buffer` (bytes, default today's 512 segments; window scaling follows the receive
buffer). Acceptance: measured with PB's netstack pair and `netstack_lossy` before/after.
MB-x6 needs no code (`NetStackStats::syn_refused` counts SYNs refused for a full listener
pool); document it for ns.

### PW: `nsplane-wss` (MC-3)

New optional crate `crates/nsplane-wss` (dependencies approved: tokio-tungstenite,
tungstenite, tokio-rustls, rustls with aws-lc-rs, rustls-pki-types; versions as already in
Cargo.lock). `nsplane` gains no dependency.

- (a) Datagram carrier: `WssDialer: nsplane::LinkDialer` ported from ns `tunnel-ws/opaque`
  (`OpaquePump`) and `examples/src/relay/wss/client.rs`: URL, TLS (system roots or a caller
  root store / pinned config), extra headers and a bearer provider trait (fresh token per
  dial), 401/403 reported as `LinkState::Rejected(u16)` (new non-exhaustive variant in
  `nsplane`, additive), doubling backoff 2 s..60 s, ping every 10 s and a 35 s read-idle
  watchdog inside its receiver, one binary message per datagram; the wire stays exactly ns's.
  The examples' relay WSS client switches to it.
- (b) Stream carrier, client leg: the WsFrame protocol (`[stream_id u32][cmd][payload]`,
  OPEN_V4/V6, DATA, CLOSE, CLOSE_ACK, as ns `tunnel-ws/frame`) over one WSS session:
  `WssStreamClient` opening TCP streams (`AsyncRead + AsyncWrite`) and UDP flows to a target,
  multiplexed (required by the user, 2026-10-03; NSGW keeps a per-session stream table,
  `nsgw-wss/src/registry.rs`, so many stream ids on one session are already accepted), with
  per-stream and per-session buffer bounds, ported from ns
  `proxy/wire.rs` + `proxy/wss_flow.rs` and `tunnel-ws/frame`.
- (c) Stream carrier, terminate leg (user, 2026-10-03 15:35: in scope now, so ns can delete
  `tunnel-ws` whole): `WssStreamServer`, ported from ns `tunnel-ws` `WsTunnel` and
  `tunnel/session` (connect to the relay, accept OPEN, stream table, per-session buffer cap
  32 MiB, separate data (256) and control (64) write queues, CLOSE/CLOSE_ACK, ping and read-idle
  watchdog, reconnect). Where an OPEN goes is the embedder's: a trait maps (target, protocol)
  to a backend address or a denial, so `OverlayResolver`, services.toml, FQID, ACL and gateway
  identity stay in ns. Stream open/close events go to an optional channel (ns
  `WssConnectionEvent`).
- e2e: the datagram carrier between two engines through a local TLS WebSocket relay
  (rcgen certificates, as the examples), 401/403 and reconnection; stream client TCP and UDP
  through the terminate leg (c), terminate denial and buffer cap, wire bytes checked against ns
  frame vectors.
