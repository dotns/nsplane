# ADR: Wintun (C library) for the Windows TUN device

Status   : Accepted
Date     : 2026-10-01
Sunset   : none (reassess if Windows gains a pure-Rust userspace TUN path)

## Context

pma-rust Lock 1 forbids new C-FFI dependencies when a pure-Rust alternative exists. Windows
has no userspace TUN API; every WireGuard implementation (wireguard-go, wireguard-windows,
gotatun) uses the signed Wintun driver through `wintun.dll`.

## Decision

- `boringtun` depends on `wintun-bindings` (MIT) for Windows only, behind the `device`
  feature. The bindings load `wintun.dll` at runtime with `libloading`; nothing is linked at
  build time.
- `wintun.dll` is not vendored. It must be placed next to the executable (or on the DLL
  search path); the matching architecture comes from <https://www.wintun.net/>.
- The `unsafe` surface on Windows is limited to loading the library
  (`device/windows/tun.rs`), the UAPI named pipe (`device/windows/pipe.rs`), and the console
  control handler (`device/windows/mod.rs`), each with SAFETY comments.

## Consequences

- Windows builds of `aws-lc-sys` need NASM on the build host; cross builds from Linux use
  mingw-w64 + nasm (`just cross`).
- The device cannot be exercised on Linux: `just test-windows` runs the unit tests under wine,
  the Wintun path needs a real Windows host.
