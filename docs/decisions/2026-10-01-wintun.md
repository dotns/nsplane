# ADR: Wintun (C library) for the Windows TUN device

Status   : Accepted
Date     : 2026-10-01 (updated 2026-10-02: Wintun is loaded by `nstun-tun`)
Sunset   : none (reassess if Windows gains a pure-Rust userspace TUN path)

## Context

pma-rust Lock 1 forbids new C-FFI dependencies when a pure-Rust alternative exists. Windows
has no userspace TUN API; every WireGuard implementation (wireguard-go, wireguard-windows,
gotatun) uses the signed Wintun driver through `wintun.dll`.

## Decision

- `nstun-tun` depends on `wintun-bindings` (MIT) for Windows only. The bindings load
  `wintun.dll` at runtime with `libloading`; nothing is linked at build time. `boringtun` no
  longer depends on it: the Windows device it carried was deleted with `boringtun::device`
  (ADR `2026-10-02-async-engine-replaces-sync-device`).
- `wintun.dll` is not vendored. It must be placed next to the executable (or on the DLL
  search path); the matching architecture comes from <https://www.wintun.net/>.
- The `unsafe` surface on Windows is a single statement that loads the library
  (`nstun-tun/src/windows.rs`), with a SAFETY comment.

## Consequences

- Windows builds of `aws-lc-sys` need NASM on the build host; cross builds from Linux use
  mingw-w64 + nasm (`just cross`).
- The Wintun backend cannot be exercised on Linux: `just test-windows` runs the unit tests
  under wine, the Wintun path needs a real Windows host.
- Since Phase 2, `nsplane-uapi` provides a UAPI named-pipe listener at
  `\\.\pipe\ProtectedPrefix\Administrators\WireGuard\<iface>` with the default security
  descriptor. Verifying the ProtectedPrefix path and the descriptor on a real Windows host
  is still pending.
